仕組み

まず、解析するプログラムはどこにいるのか

ここを外すと、あとの話がすべてぼやけます。SonarQube for IDE は「サーバーに質問を投げる窓口」ではありません。 解析エンジンそのものが拡張機能の中に入っていて、あなたの PC の上で動きます。 拡張機能をインストールした時点で、言語ごとの解析エンジンと既定のルール一式が手元にコピーされます。

あなたの PC

解析エンジン ＋ ルール表

拡張機能に同梱。ファイルを編集・保存するたびに、開いているコードをその場で読んで判定します。ネットワークに出ずに完結します。

SonarQube サーバー

チーム共通の設定

「どのルールを有効にするか」という表を持ちます。この表をチーム全員に配ることが、サーバー側の役割です。

ソースコードは、つないでも送られません。後半に出てくる「接続」でサーバーから下りてくるのは設定であって、コードが上っていくわけではありません。解析は最初から最後まで、あなたの PC の中で完結します。

検知

1 つの拡張機能が、これだけの種類をまとめて拾う

アカウントもサーバーも要りません。VS Code に拡張機能を入れてファイルを開くと、その瞬間から下線が引かれます。 文法を解釈して構文木にし、ルール表と照合する——これを入力のたびに繰り返しています。

テストコードも、同じように解析される

「テストは対象外」と思われがちですが、そんなことはありません。上の 4 件目は test_user_manager.py の中の問題です。プロダクトコードと同じ基準で読まれます。

この 5 件を判定したルールは、すべて最初から手元にある

Python の解析エンジンには 435 個のルールが同梱されていて、そのうち 398 個が最初から ON。 これが Sonar way という既定のルールセットです。残り 37 個が OFF なのは、間違ったルールだからではなく 「有効にするかどうかがチームの判断に属する」から。ON にするのはチェックボックス 1 つで、 エンジンを入れ替える必要も、コードを送る必要もありません。 裏を返せば、既定で ON の 398 個はどのチームでも「これは直すべき」と言えるものだけです。 合意形成も規約づくりもなしに、チーム全員がいきなりこの水準から書き始められます。

見どころ

テストは通っている。でも、何も守っていない

さきほどの 4 件目です。一見ふつうの assert に見えます。実際、このテストは実行され、PASS します。 壊れているのは「実行されるかどうか」ではなく、何を検査しているかのほうです。

assert (A, B) が評価される順序
書いたコード
assert (result["rank"] == "S", "管理者で高得点なら S になるはず")
assert は関数ではありません。だから括弧を付けても「引数を囲んだ」ことにはならず、タプルを作ります。
① 括弧の中身は評価される
result["rank"] == "S" → False
比較そのものはきちんと計算されています。ここまでは意図どおりです。
② その結果を第 1 要素にしたタプルが組み立てられる
(False, "管理者で高得点なら S になるはず")
この瞬間、①で出した False は袋の中に詰められ、誰にも見られなくなります。
③ assert が真偽を見るのは、このタプルそのもの
assert (2 要素のタプル) → 常に真 → PASS
空でないタプルは必ず真です。つまりこの assert は、何があっても失敗しません。

スキップされたテストなら気づけます。レポートに skipped と出るからです。これは違います。 堂々と PASS し、CI も緑になります。テストが緑である限り、CI もコードレビューも素通りする—— 気づける場所は、書いているエディタの中しか残っていません。

直し方
括弧を 2 文字消す。または assertEqual に書き換える
assert result["rank"] == "S", "管理者で高得点なら S になるはず"
self.assertEqual(result["rank"], "S", "管理者で高得点なら S になるはず")

assertEqual はそもそも関数なので、括弧を付けても壊れません。失敗したときに「S を期待したが Z だった」と差分まで出ます。保存すれば、下線はその場で消えます。

チーム

全員のエディタを、まったく同じ基準に揃える

使い始めると必ず出てくるのが、「このルールも有効にしよう」「この指摘はうちには要らない」という話です。 問題は、その決めごとが各自が手元で設定しない限り、誰の IDE にも効かないこと。 会議で決めても設定するのは半分、新しく入った人の環境は誰も知らない——こうしてチームの中に 「厳しい人の環境」と「緩い人の環境」ができていきます。

SonarQube サーバー（または SonarQube Cloud）のプロジェクトと IDE を紐づける（バインドする）と、 サーバー側で決めた品質プロファイルが、そのまま各自の IDE に降りてきます。これが Connected Mode です。

サーバー側で 1 回決めれば、バインドしている開発者全員の IDE が、まったく同じルール・まったく同じ深刻度で動きます。

コード品質とセキュリティの基準を、人に依存させずに全員へ揃えられる、ということです。

底上げ ― 決めた基準が、その日から全員に効く

「うちは外部から ZIP を受け取るので Zip Bomb のルールは必須」と決めれば、サーバー側の 1 操作で全員のエディタに届きます。判定するルールは最初から全員の手元にあるので、push もサーバーの解析待ちも発生しません。

ノイズ削減 ― 「対応しない」という判断も共有される

チームとして「この指摘は要らない」と決めたルールを OFF にすれば、全員のエディタから一斉に消えます。サーバー側で誰かが下した判断が各自の画面に反映されるので、「自分の環境だけ指摘が出る／出ない」が起きません。

新メンバーの初日から ― 規約集を覚えてもらう工程が要らない

バインドした時点で、その人の環境はチームの基準そのものになります。レビューでばらつくのはレビュアーの厳しさだけではありません。そもそも各自のエディタが違うものを見ている状態を、1 か所の設定で解消できます。

実務メモ：接続を登録しただけではルール表は下りてきません。作業フォルダとサーバー上のプロジェクトを紐づけて、はじめて届きます。また同期はリアルタイムではないので、「次にエディタを開いたときから、全員に効く」と考えておくのが正確です。
まとめ

つないでも、動いているのは 1 か所だけ

並べ替えると、Connected Mode で変わるところが 1 行しかないことが分かります。 エンジンも、見ている範囲も、応答の速さも、コードを送らないことも同じ。 変わるのは「ルールを誰が決めるか」だけです。
